这是一个基于 **PostgreSQL + `pgvector**` 插件的数据库设计方案。

**推荐理由：**
相比于维护 Redis + MySQL + Milvus 三套系统，使用 PostgreSQL + `pgvector` 可以实现**“关系型数据 + 向量数据”的混合查询**。这对于你的网关至关重要，因为你的路由策略需要同时考虑“语义相似度”（向量）和“历史满意度/价格”（关系型字段）。

---

### 1. 实体关系图 (ER Diagram 逻辑)

* **`llm_providers`**: 模型服务商/具体模型配置（价格、费率）。
* **`qa_knowledge_base`**: 语义缓存的核心表（存向量、存问答对）。
* **`chat_transactions`**: 流水日志（记录每次调用的输入、输出、耗时、Token消耗）。
* **`feedback_stats`**: 反馈数据，用于计算模型的“满意度权重”。

---

### 2. DDL 详细定义 (SQL)

请确保你的 PostgreSQL 安装了 `pgvector` 插件：

```sql
CREATE EXTENSION IF NOT EXISTS vector;

```

#### A. 模型配置表 (支撑“智能调度”的价格与配额)

这张表是路由算法的**静态数据源**，用于计算性价比。

```sql
CREATE TABLE llm_models (
    model_id VARCHAR(50) PRIMARY KEY, -- 例如 'gpt-4-turbo', 'claude-3-opus'
    provider_name VARCHAR(50) NOT NULL, -- 'openai', 'anthropic', 'local'
    
    -- 调度权重因子
    input_price_per_1k DECIMAL(10, 6) NOT NULL, -- 输入价格 ($/1k tokens)
    output_price_per_1k DECIMAL(10, 6) NOT NULL, -- 输出价格
    max_context_length INT NOT NULL, -- 上下文窗口限制
    
    -- 动态流控字段
    is_active BOOLEAN DEFAULT TRUE, -- 熔断开关
    current_latency_p95 INT DEFAULT 0, -- 近期P95延迟(ms)，由定时任务更新
    
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

```

#### B. 语义缓存表 (支撑“缓存”与“Few-shot 召回”)

这张表是网关的**第一道防线**。

```sql
CREATE TABLE semantic_cache (
    id BIGSERIAL PRIMARY KEY,
    
    -- 核心：问题与回答
    query_text TEXT NOT NULL,
    response_text TEXT NOT NULL,
    
    -- 核心：向量嵌入 (假设使用 BGE-M3 为 1024维，OpenAI 为 1536维)
    -- 注意：建立索引时维度必须固定
    query_embedding vector(1024), 
    
    -- 缓存策略字段
    intent_category VARCHAR(50), -- 意图分类：'coding', 'creative', 'chat'
    hit_count INT DEFAULT 1, -- 命中次数，用于热点分析
    
    -- 数据血缘
    source_model_id VARCHAR(50), -- 这条答案最初是由哪个模型生成的
    
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    last_hit_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 创建 HNSW 索引，加速向量检索 (至关重要)
-- opclass: vector_cosine_ops (余弦相似度) 或 vector_l2_ops (欧氏距离)
CREATE INDEX ON semantic_cache USING hnsw (query_embedding vector_cosine_ops);

```

#### C. 对话流水日志表 (支撑“历史回溯”与“难度评估”)

这张表记录每一次请求的真实情况，用于后续分析**“什么样的问题难倒了什么模型”**。

```sql
CREATE TABLE chat_logs (
    request_id UUID PRIMARY KEY, -- 每次请求的唯一ID
    user_id VARCHAR(100), -- 用户标识
    
    -- 输入信息
    query_text TEXT NOT NULL,
    query_embedding vector(1024), -- 存入向量以便离线分析或迁移到缓存表
    
    -- 路由决策记录
    routing_strategy VARCHAR(20), -- 'CACHE_HIT', 'FEW_SHOT', 'DIRECT_GENERATION'
    selected_model_id VARCHAR(50) REFERENCES llm_models(model_id),
    
    -- 执行结果
    response_text TEXT,
    tokens_input INT,
    tokens_output INT,
    total_cost DECIMAL(10, 6), -- 本次调用预估成本
    latency_ms INT, -- 响应耗时
    
    -- 状态
    status VARCHAR(20) DEFAULT 'SUCCESS', -- 'SUCCESS', 'FAILED', 'TIMEOUT'
    
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

```

#### D. 用户反馈表 (支撑“满意度评分”与“强化学习”)

这是路由算法优化的**Ground Truth (真值)**。

```sql
CREATE TABLE user_feedback (
    id BIGSERIAL PRIMARY KEY,
    request_id UUID NOT NULL REFERENCES chat_logs(request_id),
    model_id VARCHAR(50) NOT NULL, -- 冗余字段，方便快速聚合
    
    score INT CHECK (score >= 1 AND score <= 5), -- 1-5分
    feedback_text TEXT, -- 用户具体的吐槽或表扬
    
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);

-- 索引：为了快速计算某个模型的平均分
CREATE INDEX idx_feedback_model_score ON user_feedback (model_id, score);

```

### 3. 如何配合业务逻辑使用？

#### 场景一：智能缓存检索 (SQL 示例)

当用户提问时，你需要同时查询“完全命中”和“相似参考”。

```sql
-- 假设用户输入向量为 [0.1, 0.2, ... 1024维]
SELECT 
    id, 
    response_text, 
    query_text,
    1 - (query_embedding <=> '[0.1, 0.2, ...]'::vector) AS similarity_score
FROM 
    semantic_cache
ORDER BY 
    query_embedding <=> '[0.1, 0.2, ...]'::vector -- 按距离排序
LIMIT 3;

```

* **逻辑判定 (Python层处理):**
* 如果 `similarity_score > 0.95`: **直接返回** `response_text`。
* 如果 `0.80 < score <= 0.95`: 提取 `query_text` 和 `response_text` 作为 **Prompt 中的 Context (Few-shot)**。



#### 场景二：计算模型动态评分 (SQL 聚合)

为了实现“参考历史采纳模型和用户满意度”，你需要一个定时任务（如每10分钟）运行以下聚合查询，更新 Redis 中的模型权重：

```sql
SELECT 
    l.model_id,
    AVG(f.score) as avg_satisfaction, -- 历史满意度
    COUNT(l.request_id) as usage_count,
    AVG(l.latency_ms) as avg_latency
FROM 
    chat_logs l
LEFT JOIN 
    user_feedback f ON l.request_id = f.request_id
WHERE 
    l.created_at > NOW() - INTERVAL '7 days' -- 仅参考最近7天的数据
GROUP BY 
    l.model_id;

```

**路由算法公式应用：**
你从数据库拿到 `avg_satisfaction` (比如 4.5)，从 `llm_models` 表拿到 `input_price` (比如 $0.01)。

### 4. 优化建议

1. **向量维度对齐**：
* 如果你使用 OpenAI `text-embedding-3-small`，维度是 **1536**。
* 如果你使用 HuggingFace `BAAI/bge-m3` (本地部署推荐)，维度是 **1024**。
* **切记**：数据库 schema 中的 `vector(N)` 必须与模型输出严格一致，否则报错。


2. **分区表 (Partitioning)**：
* `chat_logs` 表增长极快。建议按**月**进行分区 (Range Partition)，方便定期归档旧日志，保持查询性能。


3. **JSONB 的使用**：
* 在 `semantic_cache` 中，建议增加一个 `metadata JSONB` 字段。如果未来你想做“基于文档ID的问答缓存”或者“基于用户等级的缓存隔离”，可以直接往 JSON 里塞数据，利用 Postgres 的 GIN 索引进行过滤，而不用改表结构。



这套 Schema 能够完美支撑你提出的 **Intent -> Cache -> Router -> Feedback** 闭环链路。
